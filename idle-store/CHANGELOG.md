## [1.1.5]

### Changed

> 存在并发问题，比如商品发布的时候，商品发布前读取了商品分类信息，但是之后商品分类被删除或者修改，如果被删除，那么商品不存在分类就会找不到所属分类，如果被修改，那么就会出现商品的分类信息不符合用户初始意图
> 如果要避免这个问题，在当前项目最简单的方式是商品发布时获取商品分类的写锁，但是这个写锁是锁整个商品分类表的，只有一把，势必降低商品发布的并发度，不采用
> 当某个商品分类被修改或删除时，应不允许商品发布使用此分类，只需要锁住被修改或删除的分类即可。当商品发布过程中，所选择的分类及父分类不能被删除和修改，所以要锁的是部分商品分类，不能是全表以提高并发度
> 最优方案：所有“商品绑定分类”的事务(商品增或改)，都对该分类到根节点的整条路径加共享锁；分类禁用/删除，对被修改的节点加排他锁。

- 取消 Redisson 锁，使用 MySQL 行锁
  - 分类修改时：对当前分类行加排他锁（FOR UPDATE）。同一分类的商品发布会等待本次修改结束；不相关分类不受影响。
  - 分类删除时：对待删除分类树全部节点加排他锁。该树内的商品发布、新增子分类、分类更新会等待删除结束；普通查询仍可进行快照读。
  - 分类新增时：对父分类到根的路径加共享锁（FOR SHARE），校验路径均启用后插入；避免在删除或禁用父分类期间新增子分类。
- 商品发布(未完成)发布时执行 FOR SHARE，如果分类正被修改/删除的 FOR UPDATE 锁住，数据库会自动等待。对方提交后，再读到最新分类状态并校验。
  ```java
  @Transactional(rollbackFor = Exception.class)
  public void publishCommodity(...) {
    commodityCategoryBindingGuard.checkCategoryCanBind(categoryId);
    commodityMapper.insert(...); // 或更新 category_id
  }
  ```

### Note

- 商品发布后，仍存在管理员修改了商品分类信息，之后不符合用户的分类意图了。更严格点应该是不允许“改名改变分类含义”，而是停用旧分类、新建新分类；改名仅限文字修正。
- 还有一个比如用户在打开页面后，点击发布商品前选择了分类，但是商品分类信息发生变更了，发布时确实读到的更新后的，但是从用户角度来看它只读到了发布前的商品分类信息，所以需要加 version，提示商品分类信息变更，提示重新刷新

## [1.1.4]

### Added

- 新增商品分类添加事件
- 为 redis-starter 添加 Redisson 依赖

- 引入分布式锁，为修改、新增、删除添加分布式锁

## [1.1.3]

### Added

- 商品分类删除功能补充图片失效删除，删除可能是批量删除，采用的是一个图片一个 Outbox，因为考虑分类删除事件频率低，单个图片单个Outbox更容易排查问题，当频率高或者分类下子分类数量多，比如大于50个，100个，考虑批量添加Outbox事件
- 商品更新事件中，完成更新时缓存失效问题、图片清理问题，成功时旧图标清理，失败时上传成功的新图标也需要清理
  - 更新事件+延时双删Outbox+图片清理Outbox作为一个事务，既然更新成功，就必须把图片清理掉，防止图片遗留无法被删除，同时缓存也需要失效来更新图片或者其他信息

### Fixed

- 修复完成商品分类更新中同一分类下子分类不能重名的数据库唯一键异常捕获


### Note

- 这里是保证 fileId 不会被复用，所以每次删除是安全的
- 分类删除和商品添加可能有并发窗口，比如分类删除前先检查商品为空，但是在删除前，商品添加并引用了该分类，之后分类删除，导致商品所引用的分类被清理。所以应在商品发布时检验分类状态并为分类删除添加数据库锁
- 考虑管理员较少，所以该分类操作较少考虑极端并发问题
